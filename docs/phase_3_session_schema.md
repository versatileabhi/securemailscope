# SecureMailScope — Phase 3: Zeek JSON-Log Readers and Canonical Session Schema

## Overview & Scope

Phase 3 implements the log reading, parsing, and correlation pipeline of SecureMailScope. It translates raw newline-delimited JSON logs generated by offline Zeek runs into structured, canonical session models.

Key capabilities introduced in Phase 3:
1. Safe line-by-line reading of newline-delimited Zeek JSON logs (`read_jsonl_log`) with non-fatal warning capture.
2. Canonical session schema (`CanonicalSession`) providing an anchored representation of network connections and protocol enrichments.
3. Multi-log correlation (`correlate_zeek_logs`) joining `conn.log` with `smtp.log`, `ssl.log`, and `x509.log`.
4. Lossless serialization and deserialization via standard Python dataclasses (`to_dict`, `to_json`, `from_dict`).

## Offline & Privacy Guarantees

- **No Network or Subprocess Access:** The reader and correlator are pure analytical Python modules. They make no network calls, open no sockets, and execute no subprocesses.
- **No Filesystem Writes:** Phase 3 operations are strictly read-only. No files or temporary artifacts are created or modified during parsing or correlation.
- **Path Confinement:** Input log directories are verified to reside strictly within the runtime root via `ensure_within_runtime`. Paths outside the runtime root trigger `UnsafePathError` before any file access occurs.
- **Privacy Preservation:** Absolute filesystem paths are excluded from all exported session models and correlation results. Only the directory name (`log_directory_name`) and `job_id` are retained for provenance.

## Canonical Schema Models

All models are defined in [src/securemailscope/schemas/session.py](file:///c:/Users/Sarvadnya/Downloads/SIH'26/securemailscope/src/securemailscope/schemas/session.py):

### 1. `CanonicalSession`
Primary session record representing a single Zeek connection anchored by `uid`.
- Core connection metadata: `ts`, `id_orig_h`, `id_orig_p`, `id_resp_h`, `id_resp_p`, `proto`, `service`, `duration`, `orig_bytes`, `resp_bytes`, `conn_state`, `missed_bytes`.
- Enrichment sub-models: `smtp` (`SmtpEnrichment | None`), `ssl` (`SslEnrichment | None`), and `certificates` (`list[CertificateRecord]`).
- Limitations list: explicitly embeds `PHASE_3_LIMITATIONS`.
- Ordering: deterministically sorted by `(ts or 0.0, uid)` ascending.

### 2. `SmtpEnrichment`
Enrichment sourced from `smtp.log`.
- Fields include `trans_depth`, `helo`, `mailfrom`, `rcptto`, `from_` (mapped to `"from"` in JSON serialization), `to`, `msg_id`, `subject`, `tls`, and `fuids`.

### 3. `SslEnrichment`
Enrichment sourced from `ssl.log`.
- Fields include `version`, `cipher`, `curve`, `server_name` (SNI), `resumed`, `established`, `cert_chain_fuids`, `client_cert_chain_fuids`, and `validation_status`.

### 4. `CertificateRecord`
X.509 certificate metadata sourced from `x509.log`.
- Keyed by `fuid` (file UID).
- Fields include `certificate_subject`, `certificate_issuer`, `certificate_not_valid_before`, `certificate_not_valid_after`, `certificate_key_alg`, `certificate_sig_alg`, `certificate_key_type`, `certificate_key_length`, `san_dns`, and `san_ip`.

### 5. `CorrelationResult`
Container for the complete output of a correlation run:
- `sessions`: list of `CanonicalSession` objects.
- `unmatched_smtp_uids`, `unmatched_ssl_uids`, `unmatched_cert_fuids`: lists tracking unmatched entries without discarding them silently.
- `warnings`: list of `ParseWarning` objects encountered during processing.
- Record counts: `conn_records_read`, `smtp_records_read`, `ssl_records_read`, `x509_records_read`.

### 6. `ParseWarning`
Non-fatal observable event containing `log_type`, `line_number`, `issue`, and an optional truncated `raw_line`.

## Correlation Logic & Join Paths

Standard Zeek logs are joined according to verified protocol semantics:
```text
conn.log (uid)  ──┬──>  smtp.log (uid == conn.uid)
                  │
                  └──>  ssl.log  (uid == conn.uid)
                             │
                             └── cert_chain_fuids[]  ──>  x509.log (fuid == cert_chain_fuid)
```

1. **`conn.log → smtp.log`:** Joined on connection `uid`. Unmatched SMTP records are placed in `unmatched_smtp_uids`.
2. **`conn.log → ssl.log`:** Joined on connection `uid`. Unmatched SSL records are placed in `unmatched_ssl_uids`.
3. **`ssl.log → x509.log`:** Joined via `ssl.cert_chain_fuids` pointing to `x509.fuid`. Unmatched certificate records are placed in `unmatched_cert_fuids`.
4. **Direct `conn.uid → x509.fuid` is never attempted:** In standard Zeek output, certificates are associated with TLS sessions and files, not raw connection records directly.

## Error Handling & Robustness

- **Missing Optional Logs:** The absence of `smtp.log`, `ssl.log`, or `x509.log` is non-fatal; a warning is logged, and sessions are produced with `None` enrichment.
- **Empty Logs:** Zero-byte files produce zero records without warnings.
- **Malformed Lines:** Corrupted JSON lines or non-object JSON roots produce `ParseWarning` events with line numbers, while valid lines continue to be parsed.
- **Missing or Blank UIDs:** Records lacking valid UIDs/FUIDs generate warnings and are skipped, preserving data integrity.
- **Duplicate UIDs:** Last record wins, accompanied by a `ParseWarning`.
